## 一、这是什么项目

服务器上跑的是 **DeepSeek Harness（DSH）0.2.1-rc.5**，围绕它做了三端接入 + 一堆运维加固：

| 端 | 位置 | 说明 |
|---|---|---|
| 官方 Web UI | `https://tnty.9017i.cc:19306/` | DSH 自带界面，桌面客户端就是加载它 |
| 手机 PWA（自研） | `https://tnty.9017i.cc:19306/m/` | 源码 `/root/API/dsh-mobile-web/`，当前 v136 |
| Windows 客户端 | 各电脑本地 | 源码 `/root/API/dsh-client/app/`，当前 **1.4.9** |
| 手机 App 通道 | nginx `:19305` | relay，原生 App 用 |

## 十、2026-11-07 晚补丁：列表/状态同步 + 客户端黑屏（已上线）

### 现象
1. 客户端窗口全黑，只剩菜单栏
2. 列表停在旧数据：新建的会话看不到、删掉的还在
3. running 状态反了：在跑的显示没跑、跑完的还显示在跑
4. 内网与公网两端看到的会话内容不一致

### 根因
1. **黑屏**：客户端本地代理连接池 `maxSockets: 8`，被官方界面 1Hz 的 `/dsh-purge/rewind` 轮询占满 → `GET /` 排队 >90 秒；Electron 窗口只剩 `backgroundColor`（#0f1115）就是那片黑。`/assets/*` 走本地静态缓存所以正常。
2. **列表不更新**：增量层把「新增/消失会话目录」只挂在全量对账上，而全量对账遇「有会话在跑」就无限延后——3.5 小时延后 240 次、`fullQueued=0`，检测到的 8 个新增 / 3 个消失从未落地。
3. **running 不更新**：改成「有缓存就不再启动全量」后，缓存层不再顺带登录；`/api/remote.mux` 事件监听没有 cookie 被 401 拒掉且静默重试 → running 冻结在快照时刻。
4. **内容不一致**：增量补丁抬高了 `projections.asOfSeq`，前端把 asOfSeq 当作「已覆盖到哪个 seq」，于是跳过中间内容。

### 修复
**客户端 1.4.9**（`/root/API/dsh-client/app/proxy.mjs`、`main.cjs`）
- 连接池 8 → 64（`maxFreeSockets 8`、keepAlive 15s）
- 普通 GET 加 30 秒超时；`/plugins/events`、`/agent`、`/push/`、`/api/remote.mux` 保持不超时
- `did-fail-load` 自动重试页面加载
- `session/list`：本地快照永远直出 + 按 sessionId 增量合并（新增/变化/消失/未变）+ 后台刷新单飞 + 失败退避 30s→300s；写操作不再清快照，改为后台对齐；预取复用同一份列表（启动不再各拉一次全量）

**服务端缓存层**（线上 `/root/session-cache/server.mjs`，源码副本 `/root/API/dsh-session-cache/server.mjs`）
- **mtime 增量**：每 15 秒 stat 全部日志（~18ms）；无变化直接跳过；变化会话只解尾部 zstd 帧（屏 81MB 会话约 19ms）补 `updatedAt / title / blank`
- **结构变化就地处理**：新增会话读日志头拿 `cwd`、尾部拿标题建行；消失会话直接删行；启动时做一次「磁盘 vs 快照」对账
- **不再修改 `asOfSeq`**；薄行 asOfSeq 归零
- **事件流修复**：连之前强制登录、失败打日志、cookie 失效自动重登；每 15 秒用日志写入时间兜底纠正 running（90 秒内写过=在跑；20 分钟没写还标跑=改掉）
- **全量对账**：只在空闲时执行；启动不再强制全量；兜底间隔 6 小时

## 十三、手机端 rc.2 实例（/m2/，2026-11-08 凌晨）

### 入口与鉴权
- 地址：**`https://tnty.9017i.cc:19306/m2/`**（和主手机页 `/m/` 同一份 PWA，v139 起按路径自动识别实例）
- API：`/m2/api/*` → nginx `auth_request /dshm-check`（复用主手机页登录拿到的 `dshm` cookie）→ 反代 `127.0.0.1:3081`
- rc.2 自己的登录 cookie：浏览器没有它，由 nginx 的 `/m2/login` → bridge(19393) `/m2login` **种给浏览器**（302 回 `/m2/`）
- 没登录（无 `dshm`）时：`/m2/login` 会 `error_page 401 =302 /m/`，先回主手机页输密码
- 会话列表：`/m2/m/list` → 缓存层 `19402 /m/list?inst=rc2`（缓存层直连 3081，5 秒内存缓存，8 个会话约 80ms）

### PWA 改动（v139）
- `IS_RC2 = location.pathname.startsWith('/m2')`，所有 `rpc()`、WebSocket、`/m/list` 自动加 `/m2` 前缀
- rc.2 下 401 直接 `location.replace('/m2/login')`，不走主实例的 `/_dsh/token` 跳板
- Service Worker 作用域随实例（`/m2/` 或 `/m/`）

### 验证（服务端实测）
```
GET  /m2/                        200（外壳）
GET  /m2/m/list  (带 dshm)       200 / 4318B（rc2 会话列表）
GET  /m2/login   (带 dshm)       302 + Set-Cookie(dsh-auth-…=224B) → /m2/
POST /m2/api/session/list        200 / 42098B → 8 条
WS   /m2/api/remote.mux          open ok + ready
```

### 一页切换（v140 起，推荐用法）
`/m/` 顶部多了一个「主 / rc2」按钮：点一下切换实例，选择记在 `localStorage('dshm.inst')`。
切到 rc.2 时会先走 `/m2/login?back=/m/` 让 nginx 种好 rc.2 cookie，再回到 `/m/`，全程不换页面。
`/m2/` 仍保留（路径强制 rc.2），作为兜底入口。

### rc.2 接口实测（2026-11-08）
手机端用到的远程方法**全部存在**（实测 HTTP 200 + 业务错误码，说明方法注册了）：
`session/list`、`session/page`、`session/rename|cancel|fork|selectModel|updateQueue`、`session/modelCatalog`、
`goals/get|create|edit`、`messageFeedback/put`、`workspace/pinSession|unpinSession|archiveSession`，
WS 端点 `workspace/follow` 也正常（返回 baseline，含 workspaceId/path）。
**rc.2 缺的接口**（返回 404）：`workspace/list`、`workspace/read`、`workspace/write`、`schedule/list` —— 手机端没用到，所以不影响。

### 已知限制
1. **推送只对主实例有效**（rc.2 没接 push-service，回合结束/审批不会有通知）
2. rc.2 是旧版（0.2.0-rc.2），缺失接口见上；桌面端 rc.2 走的是它自己的官方 UI，与手机不同
3. 桌面客户端 rc.2 窗口走 `/rc2/`，手机走 `/m/`（按钮切换）或 `/m2/`，两套互不影响

## 十四、手机端体验修复 + rc.2 推送（2026-11-08 凌晨 01:00）

### 修复
| 问题 | 原因 | 修复（版本） |

| 点「展开剩余 N 个」没反应 | 列表重绘的「数据指纹」没包含展开/置顶状态，改了状态但 `sig` 相同直接 return | 指纹加入 `expandedGroups`/`pinned`（v141） |

### rc.2 推送
- 新服务 `dsh-push-rc2.service`（`/root/push-service/rc2-watcher.mjs`）：用 bridge 的 cookie 连 `ws://127.0.0.1:3081/api/remote.mux` 的 `$events`，把「回合结束 / 需要审批 / 需要回答」转给主推送服务 `:19400/push/notify`，payload 带 `inst:'rc2'`
- 推送服务与订阅完全复用（不重新订阅）；通知标题带「（rc.2）」区分
- SW 通知点击链接改为 `/m/?inst=rc2&session=…`（主实例带 `inst=main`），PWA 启动时识别 `?inst=` 并切换实例（v146）
- 实测：rc.2 watcher 连上，标题刷新 9 个会话

### 运维备注
- 主实例推送服务日志确认一直在发（`推送完成 sent=1`）；若手机端收不到，先看是否还装在桌面（iOS 只有装成 PWA 才收 Web Push）

### v147：连续发多条消息，返回再进只剩第一条
- 原因：第 2 条起的消息还在服务端排队区（`session/list` 的 `projections.values.inbox.next-turn/next-step`），没落成 `user/message` 事件；重进时只按快照渲染消息、没恢复排队区
- 修复：缓存层 `/m/list`（主实例和 rc.2）多返回 `project.inbox`；PWA 进会话时用它恢复底部「排队中」条（带插队/删除）
- 实测：`/m/list?inst=rc2` 已能看到 `inbox.nextTurn`（rpcId + 文本）

### v148：列表「运行中」标记不消失
- 诊断：手机上那条「运行中」其实是真在跑（rc2 `session-6e3eca83` 最后事件 `seq=863 tool/call`，01:29:13，长任务），不是显示错误
- 但有两个真实隐患，已一起修：
  1. 列表页没有实时流，回合在别处结束时徽标会停在旧状态 → PWA 在列表页每 30 秒静默刷新一次 + 回到前台刷新
  2. 若 DSH/rc2 的 `running` 标记本身卡住（进程异常/事件丢失）→ 缓存层 `/m/list` 加兜底：`running=true` 但 20 分钟没有写入（`updatedAt` 不变）按已结束显示

### 客户端 1.5.2：公网抖动导致黑屏 / upstream error
- 现象：两台跨公网客户端同时黑屏，窗口显示 upstream error
- 证据：服务端 DSH 自 04:18:44 未重启、nginx 该客户端无 5xx、外网检测点取 `/m/` 200；该客户端 14:09:12 两条 `api/remote.mux` 同时断开后再没建过新 mux（只有后台 session/list 轮询），说明 UI 收到 1011 "upstream error" 后不再重连
- 根因：本地 ws-mux 在上游断开时用 `ws.close(1011, 'upstream error')`，DSH UI 把 reason 画到页面上并且不重连
- 修复：ws-mux 改 `terminate()`（1006 异常关闭）触发 UI 重连；proxy 静态资源断网回退旧缓存 + 自动重试页；main 检测错误页自动重载
- 发布 1.5.2（sha256 `2a505139…`），10.0.1.166 已验证
